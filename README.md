# gk-presenter

Локальная мастерская технических объяснений: исходная речь автора + доказательства из кода и графа + визуальный план + синтез авторского голоса.

Цель — сохранять манеру автора, но делать объяснения точнее, короче и понятнее. Не имитировать уверенность при недостатке доказательств.

## Текущее состояние

Это начальный репозиторий, не готовый генератор видео. Реализованы контракт сценария, валидатор, инспекция архива Camtasia и CPU smoke-test XTTS-v2. Распознавание речи, доступ к графу и автоматический монтаж ещё не подключены. Голосовой тест скачивает модель, но не загружает пользовательские данные в облако и не делает платных вызовов.

## Запуск

Нужен Node.js 22+. Зависимостей пока нет.

```powershell
npm test
npm run check
node src/check-lesson.mjs path/to/lesson.local.json
```

Валидатор проверяет структуру и ссылки между утверждениями, доказательствами и кадрами. Он не доказывает истинность текста и не открывает исходники.

## Как устроен будущий процесс

1. Подключить оригиналы видео и аудио по локальным путям, не перемещая их. Проверить длительности и сдвиг дорожек. Отдельное аудио не считать автоматически синхронным.
2. Сделать расшифровку с временными метками. Отделить оговорки и повторы от ценных авторских объяснений.
3. Через существующий оркестратор gk получить код, пути графа и готовые аннотации. Не создавать второй экстрактор и не зависеть от визуальных плиток. Фиксировать ревизию источников; старое видео может описывать старый код.
4. Собрать пакет доказательств для выбранной темы. Аннотация — вспомогательный источник, а не замена проверке реализации.
5. Подготовить сценарий и кадры: одна мысль, её доказательства, нужный фрагмент диаграммы, произношение терминов. Не показывать сразу весь граф.
6. Автор утверждает текст. Затем синтезировать речь по коротким фрагментам и измерить фактическую длительность. Подстроить кадры под речь, а не ускорять голос ради заранее придуманного тайминга.
7. Собрать аудио, визуалы и монтажный план. Проверить ударения, термины, смысл, соответствие изображения речи; только затем экспортировать ролик.

## Первый эксперимент

Выбрать 60–90 секунд из 40-минутного видео. Подготовить три версии: оригинал; улучшенный текст; улучшенный текст с клонированным голосом. Сравнить смысловую точность, понятность, узнаваемость голоса, темп и количество ручных исправлений. Измерить время генерации / длительность аудио на имеющемся CPU, прежде чем выбирать движок для полного ролика.

XTTS-v2 — кандидат, не зафиксированный выбор: требуется проверить качество русского, скорость на CPU и условия лицензии для предполагаемой публикации. Дискретная видеокарта не предполагается. Для отбора образца использовать чистую речь одного человека без музыки; не скармливать все 40 минут короткореференсному движку.

## Данные и безопасность

- `data/`, `output/`, `models/`, `*.local.json` не входят в Git. Локальные пути задаются в `sources.local.json`, шаблон — `examples/sources.example.json`.
- Только голос владельца с его согласием. Исходники не изменять и не удалять.
- Голосовые образцы, содержимое экрана, ключи API и персональные данные не публиковать. `.gitignore` не заменяет проверку перед публикацией.
- Облачные сервисы подключать только после явного выбора пользователя; локальный запуск по умолчанию.
- Автоматическая публикация на YouTube не входит в начальный объём.

## Контракт сценария

См. `examples/lesson.json`. `evidence` хранит ссылки на источники; `claims` связывает технические утверждения с доказательствами; `segments` связывает речь и визуал с этими утверждениями. `targetSeconds` — ориентир, не измеренный результат TTS. `profile` описывает аудиторию и авторскую манеру, `pronunciations` — проверенные варианты произношения.

## Локальный голосовой тест (Windows, CPU)

Нужен `uv`. Скрипт создаёт отдельный Python 3.11, не меняя системный Python. PyTorch 2.8 CPU выбран, чтобы не требовать CUDA и дополнительного TorchCodec. Поддерживаемый пакет `coqui-tts` предоставляет модель XTTS-v2; это не старый пакет `TTS`.

```powershell
powershell -File scripts/setup-voice.ps1
.venv\Scripts\python.exe scripts/voice_smoke.py --prepare-only --start 60 --seconds 12
.venv\Scripts\python.exe scripts/voice_smoke.py --start 60 --seconds 12
```

`sources.local.json` должен содержать существующий `audioPath`, `voiceConsent: true` и, для загрузки весов, `xttsLicense.accepted: true`. Это поле выставляют только после явного согласия с [CPML](https://huggingface.co/coqui/XTTS-v2/blob/main/LICENSE.txt). Модель и результат — **только для некоммерческого теста**, не для коммерческого ролика. Образец на 60-й секунде — кандидат для проверки работоспособности, а не автоматически одобренный эталон голоса. Прослушайте `reference.wav` и при необходимости задайте другой `--start`.

Каждый запуск создаёт новую папку `output/voice-test-...` с эталоном, синтезированным WAV и отчётом о скорости. `realTimeFactor = время синтеза / длительность WAV`; загрузка модели измеряется отдельно. Веса остаются в `models/`. Первый запуск требует интернета для загрузки пакетов и весов.

Архив исходного монтажа проверяется без распаковки:

```powershell
.venv\Scripts\python.exe scripts/inspect_camtasia.py
```

Наличие одинаковых записей внутри архива не доказывает совпадение с экспортом. Конец клипов, диапазон экспорта, скрытые дорожки и версия монтажа проверяются отдельно.
# Хранение материалов

## Подготовка живой сцены

Настройка кадра выполняется до записи, а не обрезкой готового видео.
Команды запускаются из `gk-presenter`:

```powershell
npm run scene:prepare -- --row 12 --sheet "!" --diagram graph/draw/generated/Fisher-Yates.drawio --session C:/GitHub/gk/tmp/fisher-yates/runtime/latest.json
npm run scene:apply -- --output <каталог-сцены>
npm run scene:check -- --output <каталог-сцены>
```

`prepare` читает текущую строку A:L через Google Sheets MCP, сохраняет параметры
и копию диаграммы в каталог из `materials.local.json`. Дополнительные параметры:
`--spreadsheet ID`, `--function STABLE_ID` вместо сессии, `--output PATH` внутри
каталога материалов. `--sheet` принимает имя листа либо `!`, `!!` и т.д.

Для текущего формата таблицы: B задаёт размер кадра, F/G задают верхнюю/нижнюю
границы. Масштаб вычисляется по полной высоте этих шагов с отступами 16 px;
H задаёт узел, который также должен полностью помещаться по ширине; проверка
отказывает, если он обрезан, не уменьшая молча заданный вертикальный масштаб.
Указка, голос, код и титры сохраняются для последующих этапов.
Это подготовка кадра диаграммы, не универсальная реализация интерактивного сценария.

Контракт каталога: `scene-preparation.json` содержит параметры, SHA-256 и ID
сессии; `scene-sheet-source.json` — исходную строку; `source.drawio` — снимок;
`runtime-session.json` — выбранный прогон; `screen-geometry.json` — проверку
реальных экранных границ. Старые `sheet-source.json`, аудио и материалы монтажа
не перезаписываются. Повторный `prepare` в тот же каталог запрещён; `apply`
повторяет замороженную настройку без повторного чтения таблицы.

`apply` работает только через мост отдельного окна презентации. `check` ничего
не передвигает. Оба шага отказывают при изменении диаграммы или сессии.
Скрипт записи строки 12 теперь требует этот контракт, проверяет формат OBS и
кадрирование и соответствие текста озвучки до `StartRecord`; его последовательность кликов остаётся отдельным
сценарием. Озвучка, запись, монтаж и публикация не запускаются командами подготовки.

Локальный файл `materials.local.json` задаёт каталоги `data` и `output` для
исходных записей, аудио, видео, кадров и метаданных сцен. На текущем компьютере
это `C:\Users\a1ole\OneDrive\gk-presenter`. Сам конфиг исключён из Git.
Рабочие скрипты используют `material_dir()` (Python) и `materialDir()` (JS).
Метаданные сцен содержат новые пути. Каталоги `data/` и `output/` внутри
репозитория больше не используются; переадресаций нет. Исторические снимки
сохраняют исходные пути и не служат рабочей конфигурацией.
Код, версионируемые сценарии, зависимости, модели и секреты остаются локально.
Наличие файлов в каталоге OneDrive ещё не подтверждает завершение облачной
синхронизации — её состояние показывает клиент OneDrive.
